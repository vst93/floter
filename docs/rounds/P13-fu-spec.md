# P13-fu 规格 — 像素细节第一格：1px 发丝线落在分数坐标上

## 意图

「1px 的线在分数坐标上会不会被摊成两行各半」——这是 P13-ft 报告「仍待」第 1 条，
也是用户那句「界面偏糊、空间感不够」唯一还没被量过的物理解释。**先量**，量出来
如果是「会摊开」，那是全仓每一条 `Border(1, …)` 的系统性问题；如果「不会」，
那这条性质此前没有任何 pin 守着，换个画法（`Shadow`/`Opacity`/模糊）就会静默退化。

## 为什么现在做

`docs/liquid-glass.md` §6 差距表**没有 `未开始` 行**，通用队列的
间距节奏 / 状态反馈 / 空态满态 / 文案密度 / 边界情况五类都已收口
（P13-aj/fi/fj/fs/ft），只剩「像素细节」。本轮取它最硬的一格。

另外核对了任务书里点名的两个「先量再改」的数，**都已经被之前的轮次结案**，
本轮不再重做：① `Float` 固定 +0.10（§2.1，P13-ac 量过、判「不改」）；
② 浅色 `LensRim`（P13-ah 已重定基线 `0.09 → 0.24`，§3 有表）。

## 现状（实测，不是推断）

- 框架 `mygo@v0.7.3/ui/paint.go:160-167` 的 `snap` 把矩形的**两条边都四舍五入**
  到整设备像素（注释原文 “so that edges stay crisp”）——所以 1px 线**不会**被摊开。
- 实测（真 `actionButton`，父级 `Padding(t.Space(2.25))`，盒顶落在分数坐标上）：

| 台阶 | `Space(2.25)` | 盒顶 Y | 浅：边 / 冠 / 面 | 深：边 / 冠 / 面 |
|---|---|---|---|---|
| tiny | 7.200 | 17.700 | 216 / 236 / 230 | 54 / 58 / 39 |
| small | 8.100 | 18.600 | 216 / 236 / 230 | 54 / 58 / 39 |
| default | 9.000 | 19.500 | 216 / 236 / 230 | 54 / 58 / 39 |
| large | 9.900 | 20.400 | 216 / 236 / 230 | 54 / 58 / 39 |

  四个台阶的**小数部分各不相同**（.7/.6/.5/.4），三行的读数**逐值相同**，
  且边行只有**一行**（盒顶上一行仍是地面 247 / 14，面从盒顶 +2 起连续）。
  ⇒ 结论一：分数坐标不产生抗锯齿，只产生 ≤0.5px 的**落点**偏移（四舍五入）。
- 结论二（副产品，记进合约）：同一条「顶边」在两种外观下读成**相反的东西**——
  浅色是「暗线 216 + 亮点 236」（边比面暗 14，冠比面亮 6），
  深色是「亮线 54 + 更亮的 58」（边比面亮 15，冠比面亮 19）。
  浅色的顶边视觉上是一条**暗描边**，深色是一条**受光边**。这一条**不改**
  （改它要动已落地的 `ControlEdge` / E1 判据），写进「需拍板」。

## 落地项

1. `internal/settingsui/hairlinegrid_test.go`（新）：四个台阶 × 深浅，
   把真 `actionButton` 放在**分数内边距**下，断言
   (a) 盒顶的 Y **确实是分数**（.7/.6/.5/.4，证明这一帧真的在测分数坐标）；
   (b) 盒顶那一行是唯一的一条边（上一行 == 地面，下一行 != 边）；
   (c) 边 / 冠 / 面 三行逐值等于上表（V 类 pin）；
   (d) 面从盒顶 +2 起至少连续三行同值（线没有往下渗）。
2. `docs/liquid-glass.md` §6.140：把这四条性质写进合约，并把
   「框架 `snap` 是这一支的地基」记下来（换框架/换画法时要重跑）。
3. 零像素改动：本轮**不改任何墨**。
