# P13-df 报告：三个画面包的夹具都在量一个生产上不存在的帧（先量，不改）

## 一句话

把「夹具没装设计主题」从四次偶发发现（P13-cm / dc / dd / de）变成一次量清的账：
`internal/launcher` **21** 个测试函数、`internal/terminalui` **8** 个、`internal/settingsui`
**四十余条** pin 量的是框架库存的 14pt / 4.0 间距，而生产画的是设计阶梯的 10.8pt / 3.6。
本轮**不改产品、不改夹具**：这一族必须独占一轮，理由与做法写进合约 §6.75 与
`.pending-bugs.md`，下一轮（P13-dg）照单执行。

## 量到了什么（全部本轮实测）

生产侧：`internal/shell/shell.go:4262` 在 surface 画之前装 `surface.Tokens.Theme`。

| | 夹具（库存） | 生产（设计） |
|---|---|---|
| `c.Theme().FontSize` | 14.00 | **10.80** |
| `c.Theme().Spacing` | 4.0 | **3.6** |

三个 `render()` 都没装主题：`internal/launcher/view_test.go:56`、
`internal/terminalui/view_test.go:22`、`internal/settingsui` 的同名助手（P13-dd 记过）。

**最值钱的一条**：库存主题下这把尺子是量子化的 —— `MeasureText("Ag")` 在 9.90 / 10.80 /
11.70 / 12.60 / 13.00 / 14.00 上全部返回 **22.0**（16.00 → 24.0、17.10 → 25.0）。
设计主题下才是 17 / 17 / 18 / 19 / 25。所以启动器那条「六档阶梯 15/18/22/24/25/28」里，
**18 / 22 / 24 三档不是三个字号**，是同一把库存尺子的三个刻度：它们描述的是夹具，
不是界面。

## 代价：给 `render()` 装主题之后，实跑变红的清单

### launcher（21 个测试函数）

阶梯 pin `[15 18 22 24 25 28]` → 实际画出 `[15 17 18 19 25 25.2]`；标题列 pin `54.0` → 生产
`48.6`；字段块地板 `y=55` → `49`。另有三类**前提破掉**的臂（`outputedges_test.go:184`
的「没有一行被切在两端」、`outputnumbers_test.go` 的「十行列表滚动」、`outputfold_test.go:171`
的「第一行只露 1.000」）：帧变了之后夹具不再进入它要测的状态 —— 这一类只能换窗口尺寸，
不能改数字。

### terminalui（8 个测试函数）

终端页阶梯 pin `[15 22 23 28]` → `[15 17 18 25.2]`；抽屉阶梯 `[17 20 22 28 30]` 里
**`20 —— 迷你终端预览的一行`** 是库存取景的产物：那一行在生产是 `10.80-1 = 9.8pt`，
画出来 **15**。抽屉滚动的那条规则在 640×360 上直接失去前提（`MaxY=0.0`，内容装得下）。

### settingsui

P13-dd 已记「四十多条 pin 在量库存字 14」，本轮未重跑（只有两条需要真数的 pin 用了
`renderThemed`）。同一份账。

## 为什么不在这一轮顺手收口

1. **规模**：21 + 8 + 40 条 pin，且每条要判 V / B / S；判不准按 B 跑，红了要区分
   「产品回归」与「夹具换了尺子」。
2. **有一类不是数字问题**：前提破掉的臂要**放大窗口**让它重新进入状态（`MaxY=0`、
   「只露 1.000」）。这类改动一旦和重钉混在一起，就再也分不清哪条是产品变了。
3. **本轮的产出是判据，不是改动**：做完这份账，下一轮每条红都有归类，不会把
   「量错了」当成「做对了」。

产品代码与测试代码本轮**零改动**（`git status --porcelain` 空 → 只有 `docs/` + `.pending-bugs.md`）。
