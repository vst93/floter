# P13-dx 报告：同一张卡两张列表的副标题差 6 级 —— 差的不是墨，是字号

方向一句话：**同一张卡里的两张列表，同一句副标题画在两个字号上，于是「同一个 token」
在小的那一个上根本覆盖不到自己的颜色；本轮把它收到阶梯上的 Body 档，并把 pin 从库存尺
搬到出货尺、删掉容差带、加一条「够得到自己的墨」的判据。**

**为什么让它更轻/更有空间感**：这条 pin 管的是**同一张卡两张列表的副标题**——它此前一直绿，
因为它量的是库存尺（字体 14）上的一帧：那一帧里两个字数都够粗，差 0。换到 app 真画的
出货尺（字体 10.8 / 9.8）上，9.8 那一支只有 **119**（token 自己是 125）——同一个墨在两个
寄存器上是两个读数，「同一档」这句话在像素上不成立。收口之后两支逐级相同（125 / 118），
副标题落在阶梯上的一档（Body 10.8）而不是一个「比正文小一档」的 9.8，跟随界面步长缩放。

**偷了什么（工艺密度菜单，逐条落数）**：

- 第 3 项「排版层级」：副标题落在**阶梯上的一档**（`tokens.Body` 10.8）而不是 `body − 1`
  （9.8 落在 Caption 9.9 与 Body 10.8 之间，不随界面步长缩放）。落值：字号 9.8 → **10.8**，
  行盒 42 → **44.8**。
- 第 6 项「编辑细节 / 精确几何」：字带的列起点从字面量 `54` 改成 `54 × designUnit()` = **48**；
  ②③ 的 `±4` 容差带删成精确相等 —— 这就是本轮的主改动之一。
- 第 9 项「一致性检查」：同一张卡的两张列表，副标题必须**同寄存器、同墨、同读数**；
  本轮把「同读数」钉成 **125 = 125 / 118 = 118**，而不是「±4 以内」。
- 第 12 项「材质细节」的克制：不新增任何墨、边、影 —— 只把已有的墨量准、把字号搬回阶梯。

**preflight 逐条**：

- **A 反套路**：无渐变 / 发光 / 斜体 / 眉批式小标题；本轮没有引入任何新视觉元素。
- **B 设计读取一致性**：设计读取一句话 =「同一张卡的两张列表，副标题同一个寄存器（Body）、
  同一个墨（`TextSecondary` / `TextMuted`）、选中只提一档不提重」；六条臂现在都在这句话上。
- **C 动效抽查**：无动效改动；出图的深色那一臂仍走 `SetDark + Advance(500ms)` 的既有路径
  （`listOutputShipped` / `renderShipped` 内置）。
- **D2 中文页**：**仍未过** —— `tokens.Caption` 9.9px / 正文 10.8px 对 preflight「正文 ≥ 14px」。
  第 **49** 份证据：本轮量到 9.8px 的描边**够不到自己的颜色**（119 vs 125），
  这是「字太小」的直接像素证据，比字号数字本身更硬。等用户拍板（不擅自改字号）。
